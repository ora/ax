# Agents

How coding agents should work in this repo. The README covers usage; this file covers the invariants.

## Key design decisions

1. **Thin client.** The CLI never scans, scores, or ranks anything locally. Every interpretation - grade, check tiers, fix ranking (`topFixes`), `estScoreGain` - comes from ora's versioned audit contract (`?format=audit`). If a rendering needs an ordering or a judgement, it must already be in the payload; re-deriving it client-side is the drift the Audit API exists to eliminate.
2. **Contract-generated types.** `src/contract/types.gen.ts` and `version.ts` are generated by `pnpm contract:gen` from the served OpenAPI spec - never hand-edited. CI regenerates from production and fails on diff, so a server-side contract bump is a red build here, not a user bug report. `openapi-typescript` is pinned to v6 (v7 needs the TypeScript compiler API, which this repo's TypeScript 7 native port does not expose).
3. **Display-only tiers.** ora's check tiers (required / recommended / emerging) carry no score weight. Report copy must never imply tier determines score; fixes are ranked by the payload's `topFixes`, rendered verbatim.
4. **`--json` is raw contract passthrough.** The payload exactly as ora served it - no reshaping, no injected fields. Scripts key on stable ids (`checks[].id`, `layers[].id`) and `contractVersion`.
5. **Exit codes are the contract.** `0` ok · `1` below `--min-score` · `2` usage · `3` API. Documented in README and `--help`; tests pin them.
6. **No third-party tunnel binary, no runtime downloads.** Tunneling a local target is either ora's own first-party tunnel (`--tunnel ora`, `src/tunnel/ora.ts`: `@ora-ai/tunnel-protocol` over Node's built-in `WebSocket`, bundled into the bin like every other devDependency - protocol code, not a vendor) or a user-supplied command (`--tunnel-cmd` / `ORA_TUNNEL_CMD`) that prints a public https URL; the CLI never ships, downloads, or hardcodes a tunnel binary. The ora tunnel stays out of the library entry (`src/index.ts`), which keeps its zero-runtime-deps promise; every tunnel audit is sent `ephemeral=1` (pinned by a test), and every exit path - success, API failure, Ctrl-C - deletes the tunnel row. Skill content is fetched from the registry and sha256-verified against the index digest, never bundled into the tarball. This package is a trust artifact.
7. **Env-first configuration.** The CLI reads environment variables (`ORA_API_URL`, `ORA_PLATFORM_URL`, `ORA_API_KEY`) and a working-directory `.env`; it never writes config.
8. **One self-contained bin, zero runtime deps.** `dist/main.cjs` bundles everything (citty, picocolors are devDependencies); the library entry (`dist/index.*`) shares the client code and also has no runtime deps. Adding a runtime dependency is a design decision, not a convenience.
9. **`ax journey` namespace is reserved.** Journey-simulation commands beyond the current one land as `ax deep-journey`; do not add subcommands under `journey`.
10. **`process.exitCode`, never `process.exit()`, after writing to stdout.** A large `--json` payload exceeds the 64KB pipe buffer and `process.exit()` truncates it mid-flush.
11. **The WebMCP capture is a copy of ora's engine, not a reimplementation.** `ax webmcp-audit` measures a page here and ora scores it there, and the same site has to get the same answer from both - so everything that decides a value on the wire is copied verbatim into `src/webmcp/vendor/` (the shim, the verdict ladder, the static signals, the check registry, the challenge predicates). Biome does not format that directory, and every file there carries a header saying so. `src/webmcp/{cdp,capture,chrome,ingest,report}.ts` is plumbing only - transport, budgets, error mapping, rendering. A judgement written by hand outside `vendor/` is the drift this arrangement exists to prevent; `deriveIframeAllow`'s tests are ora's own cases, unmodified, for exactly that reason. The version check is NOT sufficient on its own - the engine has changed this code without changing the version - so re-copy the whole directory whenever the engine moves. Three deliberate deviations, all marked inline: `collectStaticSignals` takes its inline JS as a parameter (ora derives it with an HTML parser, which would be a runtime dependency), the capture covers the entry page only, and the engine's comments have their source paths rewritten to point at this directory.
12. **The shim version is the contract; pin it from the constant.** `WEBMCP_SHIM_VERSION` (vendored in `checks.ts`) is what the ingest endpoint checks before it does anything else, rejecting a mismatch with `400 SHIM_VERSION_MISMATCH` - which the CLI renders as "upgrade ax", never as a generic API error. A capture taken by a different shim measured something else, so the version is not a label to adjust until a request is accepted: never hand-edit it, and re-copy the whole of `vendor/` from the engine revision the endpoint actually runs. Copying from a newer, unshipped revision produces captures the server refuses and, worse, captures that claim to be something they are not.
13. **Availability is a gate, not a pillar, and it is on the PUBLISHED shape only.** The terminal `done` frame carries the projection (`vendor/projection.ts`), not the stored record: it adds `contractVersion`, a non-null `evidenceCoverage`, and the derived `availability` gate that decides whether a score exists at all. A `not-ready` page has `score` and `grade` null, and with `--min-score` that is exit `1` (a failed threshold), never exit `3` - the call worked, the page is not agent-ready. A pillar reading `0` is ambiguous in the payload (earned nothing vs nothing to measure); the report resolves it from the findings, never by guessing from the number.
14. **A browser that provides WebMCP does not measure the same thing.** ora captures with a browser that has no WebMCP support, and pass A asks whether `modelContext` is present without the shim having installed it - so on a Chrome started with `--enable-features=WebMCPTesting` that reads true for every page. Three independent guards, all worth keeping: `webmcpParityWarning` reads the finished capture and says so on stderr in both output modes; the CLI launches its own flag-free Chrome rather than attaching to whatever sits on 9222 (which is where the `webmcp` plugin tells people to keep a flag-ENABLED one for `@ora-ai/webmcp-verify`); and the server annotates the affected finding itself, which is why `details` is rendered verbatim. The launched browser also mirrors ora's capture browser where it shows up in a grade: images, media and fonts refused, no host rules (ora makes localhost unresolvable, which would break this command entirely) and no `--no-sandbox` (ora needs it in a container; a developer's machine does not).

## Verification

`pnpm lint && pnpm typecheck && pnpm test:ci && pnpm build && pnpm smoke && pnpm verify:pack`. Manual runs go through `scripts/mock-scan-server.mjs` (serves the checked-in real audit fixture) rather than the live API - the daily scan budget is 30/24h per IP. `webmcp-audit` has its own stand-in, `scripts/mock-webmcp-ingest.mjs`, which replays the real ingest fixture and takes a failure mode as its second argument (`shim`, `rate`, `scoring`, `stream`) so every error branch is reachable without the live endpoint (20 ingests/24h per IP). The capture itself needs a real browser and has its own CI job (`Capture (real browser)`), because unit tests stub the browser by necessity and nothing in them would catch a broken CDP call or a pass that stopped injecting the shim: `AX_WEBMCP_LIVE=1 pnpm test:capture` runs the three passes, and `pnpm smoke:webmcp` runs the whole chain against the bundled binary and the mock. Both launch their own Chrome (no flags, throwaway profile, stopped afterwards) - nothing to start first. `AX_WEBMCP_CHROME=host:port` drives one you started instead; `AX_WEBMCP_NO_SANDBOX=1` is for containers only and is set in CI and nowhere else.

Fixtures under `src/api/__fixtures__/` are captured from real `?format=audit` responses, and those under `src/webmcp/__fixtures__/` are ora's own ingest fixtures (ora.ai through the real capture worker, then the real admission, engine and projection). Derive test variations from them with explicit deltas instead of hand-rolling payloads. The webmcp audit fixture was generated without model credentials, so four checks are `unmeasured`, coverage is 49 and the grade is correctly withheld beside a score of 77 - a withheld grade with a real score is a normal state the renderer must handle, not a broken fixture. It is also a point-in-time read of a live site, so the score moves when it is regenerated; assert on shape and on the states that matter (gate, withheld grade, unmeasured pillar) rather than pinning every number.
